# #283 decision record — keep the board, page Activity, resume first downloads

**Research complete for the immediate performance decision.** Keep one Automerge board with the existing operation representation and companion signature document. Pursue two independently useful changes: read Activity from a compact, rebuildable local index, and send already-saved files to a newly enrolled replica before switching to ordinary sync. Both outcomes were demonstrated in disposable prototypes. Deliver and qualify them separately. The decision to retain the board applies to the current 10,000-operation target. At 100,000, even the fastest tested representation took 24.87 s to reach a first response. That size remains a stress case.

The deciding distinction was between opening a replica that already has the board and getting that board onto a machine for the first time. Paging helped the former. The latter failed when the sender attempted to serialize an entirely new snapshot. Changing the operation format alone fixed neither problem. [Original research question](https://github.com/depatchedmode/pardner/issues/283) · [Detailed report and run-level measurements](https://github.com/depatchedmode/pardner/issues/283#issuecomment-7138740100)

## Experiments and verdicts

Values in a row compare matched cases unless identified as historical. Decode, service initialization, first board response, and first sync are different endpoints. The final A/B/C comparison used medians from three fresh processes per arm and size. It excluded browser rendering. ### Limits that affect the decision

On the 10k study fixture the compact index and paged read moved median service initialization from 2.84 to 2.64 s and first response from 4.85 to 3.19 s. The control already cleared 3 s on this fixture. On #209’s signed-open benchmark the upgraded baseline was 3.277 s. A follow-up on a fresh fixture built by #209’s own benchmark measured 3.712 s for the current signed open and 3.016 s with the validated compact index (five fresh processes per arm). First response fell from 5.752 to 3.569 s. The prototype missed the sub-3 s median and did not exercise first edits or convergence. [Samples and machine load](https://github.com/depatchedmode/pardner/issues/209#issuecomment-7138932011)

The timed reads had a valid index. A single offline index rebuild on the current board took 5.05 s at 10k and 301.5 s at 100k. With operations in signed messages, rebuilds took 13.95 s and 178.4 s respectively. A fresh recipient also needs an index. These runs leave live upkeep and its effect on edit acknowledgement unmeasured.

Every operation on the final read fixture was flagged for review and the fixture omitted read receipts. The 535 MB reduction counts closed files, including about 207 MB of unused SQLite page space in the control. The restart study included one change from a second signer. Its 10k compaction fixture transferred about 41 MB because it used a genesis snapshot plus one large increment. Transfer size depends on how the sender has persisted the board.

## What to build and where to track it

1. **Local reads — qualify against the existing performance issue.** Qualify the writable implementation on the [#209](https://github.com/depatchedmode/pardner/issues/209) fixture. [#307](https://github.com/depatchedmode/pardner/issues/307) owns paging. Keep #209’s signed-open and first-edit criteria in force. Serve current board state and the first page of Activity. Keep older pages, task history, links, signers, and review flags available through a compact, rebuildable index. Define stable ordering and pagination while edits arrive. Invalidate or refresh on board, signature, membership and local trust changes. Measure index upkeep during writes, first-edit acknowledgement and missing-index recovery. Test duplicate retries. Preserve #209’s signed-open metric and report first response separately; the prototype’s 3.19 s first response is a different measurement. Coordinate with [#133](https://github.com/depatchedmode/pardner/issues/133), which already tracks Activity UI behavior after UI paging landed. A backend that returns everything still incurs the full-read cost.
2. **First download.** [#306](https://github.com/depatchedmode/pardner/issues/306) owns resumable download from a serving member’s saved board and signature files. Use the hub as the first serving member and assess direct serving with #200. After enrollment, pin a consistent pair of persisted document heads, authenticate the manifest and chunk requests, and let later hub edits continue. Persist verified parts and the means of finding the same pinned copy after restart or compaction. Install both documents atomically, distinguish the local persistence barrier from the hub’s acknowledgement, make the completion receipt safe to retry, then use ordinary native sync for newer changes. Specify expiry, cleanup, stale checkpoints, membership changes during transfer and fallback when a pin is gone. Acceptance should repeat the 10k compaction and 100k restart/mixed-signer cases, exercise revocation, interrupt installation, and reopen offline. Qualify the production paths against the lifecycle model and project acceptance contract.
3. **Large-board compaction — track independently.** The download design avoids a new save on the sender. [#305](https://github.com/depatchedmode/pardner/issues/305) tracks this write-path bug. When incremental bytes reach the size of the stored snapshot, [DurableRepo](../../lib/durable-repo.js) calls the same writer before acknowledging the edit. The isolated writer failed with 3,950 MiB of WASM memory allocated on the current format. Address-space exhaustion is plausible. The failing allocation size and exact ceiling are unknown. Reproduce through an ordinary edit on a reopened 100k board, then verify compaction completes and all acknowledged edits reopen. Passing a bootstrap test cannot close it.

## Fit with the existing architecture and refactoring work

- **Thread model.** [#297](https://github.com/depatchedmode/pardner/issues/297) orders the thread-model rollout; [#294](https://github.com/depatchedmode/pardner/issues/294) owns the eventual fields, relations and labels representation. Keep the derived index independent of task-specific storage, and bootstrap opaque document chunks. Neither feature needs to choose a thread schema. Add the conversation and shared-settle workloads from [#288](https://github.com/depatchedmode/pardner/issues/288) and [#290](https://github.com/depatchedmode/pardner/issues/290) as those behaviors land. Preserve the resumable board-version semantics already used by [wait](https://github.com/depatchedmode/pardner/pull/303).
- **Module boundaries.** [#241](https://github.com/depatchedmode/pardner/issues/241) proposes separating attribution views from verification, moving current-writer views alongside Activity, and placing save pacing in DurableRepo. Put paging beside Activity; let the persistence owner capture and pin the files. Reuse the protocol paths and head comparison introduced by [#236](https://github.com/depatchedmode/pardner/pull/236). Coordinate overlapping edits without making the entire cleanup a prerequisite.
- **Transport and trust.** The [native sync roadmap](../../.cursor/plans/multi-replica-sync-roadmap.plan.md) keeps the local service responsible for the replica. Add bootstrap at the enrollment-to-native-sync handoff. [#215](https://github.com/depatchedmode/pardner/issues/215) owns the authenticated hub channel and its identity dependency [#254](https://github.com/depatchedmode/pardner/issues/254). Agree on binding and revocation with that work before shipping a chunk endpoint. Exercise catch-up against the delayed relay in [#230](https://github.com/depatchedmode/pardner/issues/230) and account for signature-document growth in [#240](https://github.com/depatchedmode/pardner/issues/240). [#200](https://github.com/depatchedmode/pardner/issues/200) owns direct peer sync, and [#299](https://github.com/depatchedmode/pardner/issues/299) owns the direct/relay desktop rehearsal. Localhost trials do not discharge those gates.
- **Recovery.** Bootstrap starts with a serving hub and an enrolled member. [#62](https://github.com/depatchedmode/pardner/issues/62) addresses loss of the hub and recovery from a survivor. This result establishes neither backup completeness nor authority replacement.

## Decision scope

The immediate decision leaves several original design questions open. Per-thread documents, alternative signature transport, private read receipts versus shared settle markers, and full attachment/deletion/export recovery were not qualified in these trials. There was no full physical-byte attribution by operation class across every requested fixture and no complete first-sync comparison of all external-text designs. Preserve those as deferred questions with their product triggers. Closing the spike records why we can move forward now.
