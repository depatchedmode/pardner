# F-030-01: an unreachable service showed "Failed to fetch"

**Unit:** qf-8 · **Findings:** F-030-01, F-067-01, F-083-05, F-085-01, F-098-02, F-137-01 · **Severity:** medium

## Problem
If the local service did not answer a board request, the browser's `TypeError` reached the UI unchanged. Task panels, forms, vein selects and Control headed the error with "Failed to fetch".

## Change
`ui-prototype/src/connection.js`: `createConnection().request` now catches errors thrown by the fetch call, including the 10-second timeout. It rethrows them as `CLIENT_UNREACHABLE` with the message "The local Pardner client did not respond. Check that it is still running, then retry." The original error is kept as `cause`. The code and message match the existing pattern in `client-api.js`. Response handling (`readResponse`) is unchanged.

## Retry behaviour is unchanged
`Pardner.jsx` clears a pending operation only for the definitive codes it lists (`STALE_UPDATE`, `CONFLICT_REQUIRES_RESOLUTION`, `INVALID_ARGUMENT`, `AMBIGUOUS_ACTOR`, `NOT_FOUND`, `OPERATION_ID_REUSED`). `CLIENT_UNREACHABLE` is not one of them, so the operation stays saved and "Retry saved request" still offers to replay it.

## Note
The message is a second copy of the text in `client-api.js`, because the change was limited to `connection.js`. A shared export would stop the two copies drifting apart.

## Tests
- `test/browser-connection.test.js`: a fetch that rejects with `TypeError('Failed to fetch')` produces `CLIENT_UNREACHABLE`. The error keeps the original as `cause`, its message does not include "Failed to fetch", and the pending operation is kept.
- `test/pardner-ui.test.js` ("shows errors where the work is", in Chromium and WebKit): when a response is lost, the panel alert names the local client, does not show "Failed to fetch", and still offers Retry.
